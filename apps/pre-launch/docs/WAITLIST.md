# Waitlist data and API contracts

**Status** Proposed · Logical schema and HTTP contract for review

## Data model

Use UUID primary keys, UTC timestamps and versioned application policies. Keep runtime and migration credentials separate. Store one canonical delivery address per subscriber. For v1 trim outer whitespace, accept email with an ASCII local part and a valid IDNA domain, normalize the domain to lowercase ASCII, preserve local-part case and aliases, and enforce length on the converted address. Do not apply provider-specific alias rules. Case variants of the local part can represent separate recipients under this policy. Owner review should confirm the tradeoff before release.

| Entity | Core attributes and constraints |
| --- | --- |
| Subscriber | ID, canonical email ciphertext, keyed lookup digest, `PENDING / ACTIVE / UNSUBSCRIBED / DELETION_PENDING`, current consent generation, preferred locale, created, updated, verified and unsubscribed timestamps. Unique lookup digest. Index `(status, verified_at, id)`. Envelope keys and lookup keys are separate. |
| ConsentEvent | Subscriber FK, generation, consent version, locale, timestamp, source category and event `GRANTED / VERIFIED / REVOKED`. Unique per (subscriber, generation, event); change purpose only via new consent. Keep published policy revisions with content digests. |
| EmailToken | Selector, subscriber FK, generation, purpose, digest, key version, issued/expiry times, consumed/revoked times. Unique selector and digest. Partial unique current token slot per (subscriber, generation, purpose), cleared atomically on expiry/replacement. Indexed by expiry. |
| Suppression | Keyed email digest, reason, provenance, recorded/expiry dates; single entry per digest and reason. No plaintext email. A complaint or hard bounce persists per approved policy independently of subscriber state. |
| Campaign and EnrollmentEpoch | One stable official-launch key, state, active revision, cutoff epoch, approved maximum, remaining admission count and materialization cursor. A singleton epoch records the boundary between existing and later verifications. Store the verified epoch on the current subscriber generation. |
| CampaignRevision | Campaign FK, revision number, immutable subject/body/sender/CTA/template snapshot and content digest. Unique revision per campaign. Immutable after preview. |
| Approval | Campaign and revision FK, actor, revision digest, approval key, recipient ceiling, live/test scope, UTC timestamp. Unique live approval per campaign; transactional audit event. |
| Delivery | Purpose, subscriber FK when applicable, consent generation, campaign FK when applicable, provider ID, state and timestamps. Unique (campaign, subscriber) for live sends. Unique logical key for verification/token issue, confirmation/generation and test request. Provider ID unique when present. |
| Job and DeliveryAttempt | Delivery FK, stable ID, kind, run-after, state, lease token/expiry, attempt limit, first possible submission timestamp, immutable provider payload reference. One delivery job per delivery and one materialization job per approved campaign. Attempts unique by (job, attempt number). Partial indexes for due and expired leases. |
| WebhookReceipt | Provider/event ID as composite unique key, provider message ID, type, event time, receipt and processing status, minimized encrypted projection for unmatched events. Index provider message ID and unprocessed receipts. |
| OperatorGrant, AuditEvent, RateBucket | Unique operator by trusted issuer and immutable subject. Audit actor, action, resource, outcome, timestamp and opaque request ID. Counters use scoped keyed identities, bucket start, expiration and unique scope/bucket. |

Establish foreign keys, explicit cascade versus anonymization behavior and checks for nullable state-specific fields. Use an independent encrypted operational deletion/suppression ledger for restore reconciliation, under the approved privacy schedule. Use enrollment epoch → campaign → subscriber → delivery/job lock order for participating rows. Serialize privacy mutations, suppression updates and final send admission on the same affected subscriber. Recheck under lock after resolving unique conflicts. Use advisory locks only if a proven transaction invariant needs one. Design legacy data migration only if real legacy data is later approved.

## State transitions and token handling

1. **Subscribe.** Validate body, email, affirmative consent against the current policy version, locale, origin and abuse proof. Rate-limit before mail admission. In one transaction lock or insert Subscriber and add grant, token, delivery and outbox job. ACTIVE and suppressed records return the same accepted shape with no new mail. PENDING resends only within a proposed cooldown and per-address cap. Supersede the prior unconsumed verification token, preserving the current consent unless the disclosed policy changed and the visitor gave a new grant. UNSUBSCRIBED starts a new PENDING generation after affirmative consent, without bypassing bounce or complaint suppression. DELETION_PENDING blocks mail and re-enrollment until the approved workflow completes.
2. **Verify.** Public GET displays a confirmation button and leaves state unchanged, including when security scanners follow the link. Confirmation POST compares digest in constant time, checks purpose, current generation, expiry, consent and suppression, then consumes the verification token and atomically activates the subscriber and queues confirmation. Parallel verified retries return the same safe outcome without reactivation or duplicate mail. Stale, failed or unknown credentials receive a generic invalid/expired result. No token reuse across purposes.
3. **Unsubscribe.** Each consent generation has an opaque unsubscribe credential usable in the browser and by RFC 8058 POST. Old messages can still unsubscribe the address's current subscription while the credential remains valid, including after re-consent. Preserve prior unsubscribe credentials until the approved retirement window, or revoke on deletion. Browser GET only renders the confirmation control. A valid mutating request immediately revokes sending eligibility, cancels queued work, and records the affected consent generation. Return a generic success on repeats and expose no address. Provide a privacy contact for old or unavailable links.
4. **Generate and store.** Use cryptographically random selectors of at least 128 bits and high-entropy authenticators. Store token digests. For durable mail rendering, derive the authenticator from a separate server HMAC secret and a versioned purpose/selector/generation context so a worker can reconstruct the same URL across retries. Keep verification, unsubscribe, lookup and encryption keys scoped and versioned. Use separate rate limits and minimize secret exposure. Key loss or compromise follows the rotation and incident plan.

Browser token links prefer a URL fragment exchanged by the same-origin page and discarded before any further navigation. Offer a manual paste-code fallback for clients that strip fragments. RFC 8058 needs an HTTPS URL with the credential accessible on POST; use a dedicated route, filter that path from logging/analytics where supported, and assess provider logging before production. Apply `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, a restrictive CSP and zero third-party resources on token pages. [RFC 8058](https://www.rfc-editor.org/rfc/rfc8058)

## API

Prefix below is `/api/v1`. JSON requests use UTF-8, unknown fields fail validation, and ordinary JSON mutations require same-origin and CSRF protection as applicable. Native same-origin form submission may use form encoding from the public page through the same validator, with 303 to a safe result page. Cap JSON bodies at a proposed 4 KiB and webhook bodies at 128 KiB after provider sampling. IDs are opaque UUIDs. Use generic error bodies `{ error: { code, requestId } }`. Honor bounded `Retry-After` where applicable.

| Method and route | Request and authorization | Success and failure behavior |
| --- | --- | --- |
| POST `/waitlist/subscribe` | `email, consent: true, consentVersion, locale?, challengeToken`. Public with origin and admission controls. | 202 generic accepted. 400 invalid input/challenge, 409 policy refresh, 429 IP/global limit, 503 unavailable. Address-specific suppression/throttling indistinguishable from 202. |
| POST `/waitlist/verify` | `token`, same-origin browser. | 200 verified or previously processed. 400 invalid/expired. 429 partition limits. |
| POST `/waitlist/unsubscribe` | `token`, same-origin browser. | 200 generic idempotent result. |
| GET and POST `/waitlist/one-click/{token}` | GET confirmation view. POST `List-Unsubscribe=One-Click` as form URL encoding or multipart. Scoped credential; no cookies or origin dependence. | GET never mutates. POST 204 for a valid or already-processed request; rate and size limited. Dedicated auth policy. |
| POST `/admin/campaigns` | Owner or operator. `subject, bodyVersion, launchUrl`. Strict URL allowlist and template fields. | 201 draft; unique official-launch key enforced. |
| POST `/admin/campaigns/{id}/revisions` | Owner or operator. `expectedRevision, subject, bodyVersion, launchUrl`. | 201 immutable revision or 409 stale/state conflict. |
| POST `/admin/campaigns/{id}/preview` | Owner or operator. `revisionId`. | 200 rendered artifact, revision digest and estimate/as-of. No delivery. |
| POST `/admin/campaigns/{id}/test` | Owner or operator with fresh MFA. `revisionId, testRecipientId`, idempotency key. | 202 restricted test scheduled. Bounded and separate from live deliveries. |
| POST `/admin/campaigns/{id}/approve` | Owner with fresh MFA. `revisionId, digest, maxRecipients, confirm`, idempotency key; recorded delivered test for same revision required. | 202 scheduling authorized. Mismatched revision, exceeded bound or stale preview yields 409. |
| POST `/admin/campaigns/{id}/pause`, `/resume`, `/cancel` | Owner with fresh MFA and expected state; idempotency key. | 202 idempotent transition or 409 invalid state. |
| GET `/admin/campaigns/{id}` | Owner or operator. | 200 aggregate state, totals, preview revision and timestamps. No subscriber-list endpoint. |
| POST `/admin/privacy-requests` | Owner with fresh MFA. Validated address and request type; dedicated operator-only workflow tied to a support request reference. | 202 generic case admission. An existing case is reused. Queue purpose-scoped verification when applicable. |
| POST `/privacy/verify-deletion` | Dedicated token. Explicit same-origin confirmation. | 202 verified erasure queued or previously accepted. Invalid or expired proof receives generic 400. |
| POST `/webhooks/email` | Provider signature, raw body and event ID. | 204 persisted/deduplicated; 400/401 invalid input/auth, 503 temporary persistence failure. |
| GET `/internal/cron/delivery` | Scheduler bearer secret. Same route has no public/browser capability. | 204 bounded run completed or overlap skipped; sanitized status via telemetry. |

Authentication failure is 401 and insufficient role/factor is 403 on protected routes. Return `Cache-Control: no-store` on admin, tokens and mutation responses. A valid provider webhook is acknowledged only after its receipt is committed. [Campaign and outbox design](EMAIL_OPERATIONS.md) · [Privacy and deletion](SECURITY_PRIVACY.md)

Persist a bounded PrivacyRequest with unique support reference, request state, subject/digest where needed, purpose-bound credential and timestamped evidence. Remove contact reference and secrets following completion or case expiry. Contact proof does not grant any administrator authority.
