# Կանոնների և փաստաթղթերի ուղեցույց

Այս ֆայլը ընթերցման քարտեզ է։ Այն բացատրում է, թե ռեպոյի յուրաքանչյուր կանոն և փաստաթուղթ ինչի համար է, երբ է գործում, և ինչ չի որոշում։

Այն ինքը որոշում չէ։ Եթե այս էջը և աղբյուր ֆայլը տարբերվեն, գործում է աղբյուրը։ Կարգի աղբյուրը [`AGENTS.md`](../AGENTS.md)-ն է։ Արտադրանքի աղբյուրը [`README.md`](../README.md)-ն է։

Կարգավիճակը Concept & Planning է։ Հավելվածի կոդ, `docs/TECH_CARD.md` և `docs/01-ARCHITECTURE.md` դեռ չկան։

## Ինչպես կարդալ

Որոշման կարգը, ինչպես հիմա գրված է `AGENTS.md`-ում.

1. Անվտանգության անփոփոխ սահմաններ։
2. Աշխատանքի կարգ և հաստատման դարպասներ։
3. Սեփականատիրոջ հաստատած առաջադրանք և `README.md`-ի արտադրանքի շրջանակ։
4. Հաստատված `docs/TECH_CARD.md` և `docs/01-ARCHITECTURE.md`, երբ դրանք ստեղծվեն և հաստատվեն։
5. Հաստատված նախագծի փաստաթուղթ և հաստատված իրականացում։
6. Կաղապար, օրինակ և ընդհանուր ինժեներական լռելյայն։

Ցածր դասը չի դառնում բարձր դաս միայն այն բանի համար, որ պատճենվել, գեներացվել կամ քննարկվել է։ Զրույցի նախընտրությունը հաստատված որոշում չէ։

Անվտանգության բացառության գրանցամատյան չկա։ `docs/SECURITY_EXCEPTIONS.md` չկա և այս ուղեցույցը այն չի ստեղծում։ Քանի դեռ այդ գործընթացը և գրանցամատյանը սեփականատերը առանձին չի հաստատել, բացառություն վավեր չէ։

## Արմատի փաստաթղթեր

### `README.md`

Արտադրանքի միակ աղբյուրը։ Նկարագրում է Meduzellar ընկերությունը և առաջին նախագիծը՝ Meduzellar Platform։ Հինգ ուղղություն կա. Marketplace, մասնագիտական ցանց և հավաքագրում, հաղորդակցություն և տեսազանգ, realtime թարգմանություն, և սեփական օգնական։ §9-ը կարգավիճակն է՝ Concept & Planning։ Նկարագրված հնարավորությունները տեսլական են, ոչ թե կառուցված համակարգ։ §10-ը հետագա նախագծերն է և այս ռեպոյից դուրս է։ §11-ը բրենդի փիլիսոփայությունն է. Meduza + Stellar։

README-ն չի ընտրում framework, բազա, հոսթինգ կամ վճարում։

### `AGENTS.md`

Ռեպոյում աշխատելու կարգը։ Ասում է, թե էական աշխատանքից առաջ ինչ կարդալ, որտեղ են կանոնները, skill-երը և catalog-ը, և ինչն է արգելված առանց հստակ հանձնարարության։

Այստեղ է վեց դասի աղյուսակը, անվտանգության ութ անփոփոխ սահմանը, որոշման կարգը և հակասության յոթ քայլը։ Անվտանգության սահմանը թուլացնող ձևակերպումը կանգնեցնում է աշխատանքը։ Տեխնոլոգիայի հաստատումը scaffold-ի, production դեպլոյի, production migration-ի կամ անվտանգության սահմանը հանելու թույլտվություն չէ։

Աշխատանքի սահմանները մնում են նույնը. չփոխել ճարտարապետություն, stack, հրապարակային API, սխեմա կամ բիզնես վարք առանց հաստատված առաջադրանքի, չանել production դեպլոյ կամ production migration, չջնջել տվյալ, չանել commit կամ push առանց հստակ խնդրանքի, չթուլացնել անվտանգության վերահսկողություն ստուգումը անցնելու համար, չհորինել բանալի։

### `00-core.mdc`

Միշտ գործում է, բոլոր ֆայլերի վրա։ Ընդհանուր կարգն է։

Արգելում է `any`-ն առանց գրանցված բացառության, գաղտնիքը կոդում, SQL-ի կառուցումը օգտատիրոջ տեքստը կպցնելով, `eval`-ը, production-ում `console.log`-ը, մեռած մեկնաբանված կոդը, թեստ ջնջելը կամ lint-ը անտեսելը ստուգումն անցնելու համար։ CORS-ը կամ CSRF-ը անջատելը անվտանգության բացառություն է։ Այս ռեպոն գրանցամատյան չունի, ուստի առաջադրանքը դա չի կարող հաստատել։

Միշտ պահանջում է արտաքին մուտքի վավերացում և սխալների գրանցում առանց լռելյայն կուլ տալու։ TypeScript-ի strict ռեժիմը պահանջվում է այն ժամանակ, երբ հաստատված լեզուն TypeScript է, ոչ թե նախքան այդ ընտրությունը։

Decisions բաժինը կրկնում է `AGENTS.md`-ի անվտանգության սահմանները, այդ թվում սերվերային լիազորությունը, գաղտնաբառի հեշավորումը, պարամետրացված հարցումները և գաղտնիքի չարտահոսումը։ Տեխնոլոգիայի կարգն այդ սահմաններից ցածր է։ Անվտանգության հակասությունը կանգնեցնում է աշխատանքը։

Կանոնների ցուցիչը այս ֆայլի վերջում է։ Տարբերակը 3.1 է, ամսաթիվը 2026-11-20. այդ տողը չի թարմացվել վերջին անվտանգության խմբագրումներից հետո։

### `01-architecture.mdc`

Բեռնվում է առաջադրանքով։ `globs` դատարկ է։

Meduzellar-ը հաստատված չափ կամ դասավորություն չունի։ `src/`, `apps/` կամ `packages/` չստեղծել, քանի դեռ TECH_CARD-ը չափը չի գրել։ Հինգ դոմենը պետք է մնան առանձին սահմաններով։ A, B և C դասավորությունները կաղապարային տարբերակ են, ոչ թե ընթացիկ կառուցվածք։ Feature մոդուլի հրապարակային մուտքը `index.ts`-ն է։ `shared`-ը չի կախվում `features`-ից։

### `02-product.mdc`

Միշտ գործում է։ Արտադրանքի սահմանն է և կրկնում է README-ի հինգ դոմենը։

Հստակ ասում է. հայտարարությունը աշխատանք չէ, հաղորդակցությունը չի տնօրինում վարձումը, թարգմանությունը չի տնօրինում զանգը, օգնականը չի տնօրինում հայտարարությունը, աշխատանքը կամ հաղորդագրությունը։ Ինտերֆեյսի i18n-ը realtime թարգմանություն չէ։

Մինչև առանձին հաստատում դուրս են հետագա Meduzellar նախագիծը, stack-ի, հոսթինգի, վճարման, պահոցի, փոստի, realtime-ի և մոդելի մատակարարի ընտրությունը, հավելվածի, սխեմայի կամ հրապարակային API-ի scaffold-ը։ Next.js-ը, NestJS-ը, Neon-ը, Prisma-ն, R2-ը, Resend-ը և Auth.js-ը կաղապարային լռելյայն են, ոչ թե նախագծի որոշում։

Երբ համակարգը կառուցվի, զգայուն են վճարումը, թվային առաքումը, անձնական և ընկերության պրոֆիլը, հավաքագրման տվյալը, զանգի և հաղորդագրության բովանդակությունը, թարգմանության տեքստը և օգնականի prompt-ը։

### `03-typescript.mdc`

Գործում է `*.ts` և `*.tsx` ֆայլերի վրա։ Պահանջում է `strict: true`, արգելում է չարդարացված `any`-ն, `@ts-ignore`-ը առանց բացատրության, և տիպային `as`-ը սխալը թաքցնելու համար։

Այս ֆայլը strict-ը գրում է որպես անվերապահ, մինչդեռ `00-core.mdc`-ն այն կապում է TypeScript-ի հաստատման հետ։ Քանի դեռ TypeScript-ը TECH_CARD-ում հաստատված չէ, լեզուն ընտրված չէ։ Հակասության դեպքում գործում է `AGENTS.md`-ի կարգը. լեզուն արտադրանքի և stack-ի որոշում է, իսկ strict-ը այդ լեզուն ընտրելուց հետո պարտադիր է։

### `04-react-nextjs.mdc`

Գործում է `*.tsx`, `app`, `components` և `features` ուղիների վրա։ Ինքն է ասում. կիրառել միայն այն բանից հետո, երբ TECH_CARD-ը ընտրի React և Next.js։ Մինչ այդ համապատասխան ֆայլեր չստեղծել միայն կանոնին հետևելու համար։

Երբ այդ ընտրությունը լինի, Server Component-ը լռելյայն է, `'use client'`-ը նեղ սահման է, նկարի և հղման համար նախատեսված են `next/image`-ը և `next/link`-ը։

### `05-backend-nestjs.mdc`

Գործում է `api`, `server`, `backend`, service, controller և module ֆայլերի վրա։ Կիրառել միայն TECH_CARD-ը NestJS ընտրելուց հետո։ Մինչ այդ controller, module կամ service չստեղծել կանոնին հետևելու համար։

Երբ ընտրվի, controller-ը բարակ է, բիզնես տրամաբանությունը service-ում է, մուտքը վավերացվում է սահմանին։

### `06-database.mdc`

Գործում է Prisma, `db`, `database` և migration ուղիների վրա։ PostgreSQL-ը և Prisma-ն կաղապարային լռելյայն են, ոչ թե Meduzellar-ի որոշում։ Սխեմա կամ migration չավելացնել, քանի դեռ քարտը դրանք չի ընտրել։

Պահանջում է պարամետրացված հարցում, runtime և migration իրավունքների բաժանում, գաղտնագրված միացում production-ում, երբ մատակարարը դա ունի։ Ժամանակային սահմանների թիվը չի դրվում լռելյայն. այն համաձայնեցվում է։ Production migration-ը առանձին թույլտվություն է պահանջում։ Քայլերը `safe-database-migration` skill-ում են։

### `07-api-design.mdc`

Գործում է `api`, controller և `routes` ուղիների վրա։ REST ձև, ճիշտ HTTP կարգավիճակ, մուտքի վավերացում, էջավորում, կոտրող փոփոխության դեպքում `/v1/`, վճարման և մեկ անգամ ստեղծելու գործողության idempotency, webhook-ի ստորագրություն։ CORS-ը և հաճախականության սահմանը ուղարկում է `08-security.mdc`։ Zod-ը այստեղ օրինակ է, ոչ թե ընտրված գրադարան։

### `08-security.mdc`

Գործում է `auth`, `api`, middleware և env ֆայլերի վրա։ Միշտ միացած չէ։ Միշտ գործող պատճենը `00-core.mdc`-ում և `AGENTS.md`-ում է։ Մարդու ստուգաթերթի հղումը `0 Security List.md`-ն է։

Արգելում է գաղտնիքը կոդում, լոգում և client bundle-ում, `eval`-ը, SQL-ի կպցնելը, գաղտնաբառի և թոքենի լոգումը։ CORS-ը և CSRF-ը պարտադիր են։ Դրանք անջատելը բացառություն է, և գրանցամատյան չկա, ուստի առաջադրանքը, զրույցը, TECH_CARD-ը կամ սովորական հաստատումը դա չի թույլատրում։ Եթե իրականացումը կարծես պահանջում է անջատել, աշխատանքը կանգնում է և հակասությունը զեկուցվում է։

Auth բաժինը դեռ ասում է չգրել սեփական token կամ session իրականացում առանց հստակ կարիքի և անվտանգության review-ի, և գաղտնաբառի համար կաղապարային լռելյայն է նշում argon2id-ը։ Դա առանձին չլուծված թեմա է։ Auth.js-ը և Clerk-ը կաղապարային տարբերակ են, ոչ թե պահանջ։

API բաժինը պահանջում է body, query և params վավերացում, CORS allowlist, webhook-ի ստորագրություն։ Responses բաժինը արգելում է production պատասխանում stack trace։ Dependencies բաժինը պահանջում է մաքուր audit։ Critical խոցելիությունը չի անտեսվում, չի ճնշվում և չի ընդունվում միայն այն բանի համար, որ ticket կա։ Ticket-ը հետևում է, ոչ թե բացառություն։ Չլուծված Critical-ի դեպքում աշխատանքը կանգնում է, և զեկուցվում են կախվածությունը, հայտնի նույնացուցիչը, բաղադրիչը և ապացույցը։

Headers բաժինը դեռ օրինակ է տալիս Next-ի `headers()`-ը և Nest-ի `helmet`-ը։ Դա framework-ի ընտրություն չէ։

### `09-figma-design.mdc`

Գործում է `*.tsx`, `components`, `styles` և `ui` ուղիների վրա։ Figma-ից կոդի ամբողջ քայլը `figma-to-production` skill-ում է։ Կանոնը պահանջում է դիզայնի token, սպեցի տարածություն, հարմարվող դասավորություն, իմաստալից HTML և առկա primitive-ների վերօգտագործում։

### `10-testing.mdc`

Գործում է թեստ ֆայլերի և `tests` թղթապանակի վրա։ Թեստը ընտրվում է ըստ ռիսկի, ոչ թե ամեն փոփոխության համար նույն խառնուրդով։ Առաջնահերթ են բիզնես տրամաբանությունը, auth-ը, վճարումը, իրավունքը, տվյալի ամբողջականությունը և ռեգրեսիան։ Ծածկույթի թիվը չի փոխարինում վարքի ստուգմանը։ Թեստ չի ջնջվում CI-ն կանաչ դարձնելու համար։ Ավարտի ստուգման հաջորդականությունը `verify-before-completion` skill-ն է։

### `11-documentation.mdc`

Գործում է `docs`, `*.md` և README ֆայլերի վրա։ Փաստաթուղթը համաչափ է հաստատված TECH_CARD-ին։ Արմատային README-ն տեղադրման ուղեցույցով չի փոխարինվում։ Run, test և env հրահանգ ավելանում է միայն հավելվածի գոյությունից հետո։ Էական ճարտարապետական որոշումը ADR է։ Հրապարակային API-ն փաստաթղթավորվում է, երբ այն գոյություն ունենա։

### `12-error-handling.mdc`

Գործում է `*.ts` և `*.tsx` ֆայլերի վրա։ Սխալը տիպավորված է և ունի կայուն `code`։ Production պատասխանը չի վերադարձնում stack, ուղի կամ գաղտնիք։ Մանրամասը մնում է սերվերի լոգում և խմբագրվում է։ Տեքստը Nest filter կամ Next route է նշում որպես հնարավոր տեղ. դա գործում է այն ժամանակ, երբ այդ framework-ը հաստատված է։

### `13-git-workflow.mdc`

Բեռնվում է առաջադրանքով։ Ճյուղը և commit-ը հետևում են ռեպոյի կոնվենցիային։ Եթե կոնվենցիա չկա, նախընտրելի են նեղ ճյուղ և Conventional Commits։ Pull request-ը փոքր է և ինքնաստուգված։ `main` կամ `develop` չի արվում force-push։ Գաղտնիք commit չի մտնում։

### `14-ops.mdc`

Գործում է `api`, `server` և `backend` ուղիների վրա։ Միացնում է նախկին դիտելիության և հուսալիության կանոնները։ Պահանջում է կառուցվածքային լոգ, request id, գաղտնիքի և ավելորդ անձնական տվյալի խմբագրում, ելքային կանչի timeout, սահմանափակ retry միայն անվտանգ կրկնվող գործողության համար, և թեթև health ստուգում։

Ֆայլը հիշատակում է `pino`, Sentry, Vercel, Render և Cloudflare։ Դրանք այս կանոնի օրինակներն են այն ենթակառուցվածքի համար, որը դեռ ընտրված չէ։ Մատակարար ընտրելը TECH_CARD-ի գործն է։

### `15-performance.mdc`

Գործում է `app`, `components` և `*.tsx` ուղիների վրա։ Core Web Vitals, փաթեթի չափ, դանդաղ հարցում և քեշ։ Redis-ը և հերթը գրված են որպես գործիք, երբ դրանք արդարացված են, ոչ թե որպես արդեն ընտրված ծառայություն։

### `16-state-management.mdc`

Գործում է `*.tsx`, hooks, store և features ուղիների վրա։ Սերվերային տվյալը, URL-ի վիճակը, ձևը, տեղային վիճակը և ընդհանուր client վիճակը տարբեր տեղեր են։ Սկսել տեղային վիճակից։ Ընդհանուր պահոց օգտագործել միայն երբ վիճակը իրոք մի քանի տիրոջ է պատկանում։ Սերվերային տվյալը չկրկնօրինակել գլոբալ պահոցում։ Գրադարանը հաստատված քարտից է, ոչ թե կանոնից։

### `17-cicd.mdc`

Գործում է `.github`, Dockerfile և docker-compose ֆայլերի վրա։ Պահանջում է ստուգումների օգտակար հերթ, կողպված տեղադրում, գաղտնիք միայն Actions secret-ում կամ OIDC-ում, ոչ թե workflow ֆայլում։ Migration-ը ուղարկում է `06-database.mdc` և `safe-database-migration`։

Կառավարվող հոսթի օրինակները Vercel, Railway, Render և Fly են։ Անունը օգտագործելի է միայն TECH_CARD-ում `Approved` լինելուց հետո։ CI-ն կամ դեպլոյը միացնելը onboarding-ի Phase C-ի առանձին թույլտվություն է պահանջում։ Օրինակները `docs/reference/workflows/`-ում են։ Այս ռեպոյում workflow դեռ չկա։

### `20-i18n.mdc`

Գործում է `locales`, `i18n`, `messages` և middleware ուղիների վրա։ Ինտերֆեյսի լեզուն և զանգի կամ չատի realtime թարգմանությունը տարբեր համակարգեր են։ Կատալոգի գրադարանը կիրառվում է միայն TECH_CARD-ը այն ընտրելուց հետո։ `next-intl`-ը և `react-intl`-ը ֆայլում օրինակ են։ Լեզուների ցանկը BRIEF-ում դեռ բաց է։

## Ակտիվ workflow-ներ

Սրանք կանոնի փոխարեն չեն։ Դրանք կոնկրետ աշխատանքի քայլեր են `.agents/skills/`-ում։ Library-ի չորս skill-ը catalog-ում կա, բայց գործող agent-ի համար բացված չէ, որովհետև տեղադրիչ չկա։

### `project-onboarding`

Գործում է, երբ README-ից և BRIEF-ից պլան է պատրաստվում։ Սովորական ֆիչի համար չէ։

Phase A-ն պլան է և հաստատում. չափ, դատարկ TECH_CARD, հետո ճարտարապետության սևագիր։ Արժեքը դատարկ է, քանի դեռ սեփականատերը այն չի տվել։ Մինչև հաստատում Decision state-ը միայն `Candidate` կամ `Proposed` է։ Phase A-ն հավելված չի կանգնեցնում, կախվածություն չի ավելացնում, սխեմա չի ստեղծում և CI չի միացնում։

Phase B-ն հավելվածի նախաձեռնում է և սկսվում է միայն առանձին բացահայտ թույլտվությամբ, երբ Phase A-ն ավարտված է և օգտագործվող ամեն արժեք `Approved` է։

Phase C-ն CI, դեպլոյ և թողարկում է, նույնպես առանձին թույլտվությամբ։ Production դեպլոյը և production migration-ը իրենց սեփական թույլտվությունն են պահանջում։ `docs/PROGRESS.md` գրելը Phase C չէ։

Կանգ է առնում, եթե BRIEF-ի պարտադիր հարցը բաց է, չափը կամ քարտը հաստատված չէ, կաղապարը կամ զրույցը գրվելու է որպես `Approved`, կամ հաջորդ քայլը scaffold, կախվածություն, սխեմա, CI, դեպլոյ կամ թողարկում է առանց այդ փուլի թույլտվության։ Զրույցի identity նախընտրությունը քարտում չի գրվում, քանի դեռ սեփականատերը բացահայտ չի խնդրել գրանցել։

### `debug-first`

Բագ, ռեգրեսիա, սխալ վարք։ Նախ վերարտադրում և պատճառ, հետո կոդ։ Սովորական նոր ֆիչի համար չէ։

### `verify-before-completion`

Էական փոփոխությունից հետո ստուգում, նախքան ավարտ հայտարարելը։ Չի ասում, թե բոլոր թեստերն անցել են, եթե դրանք չեն գործարկվել։ Բացատրություն միայն տվող աշխատանքի համար չէ։

### `safe-database-migration`

Սխեմայի փոփոխության պլան, ստուգում և ստեղծում։ Առաջին քայլում չի ենթադրում Prisma։ Production կատարումը կանգնում է առանց բացահայտ թույլտվության։ Սովորական կարդալու հարցումը այս skill-ով չի գնում։ Ռիսկի ուղեցույցը `references/migration-risk-guide.md`-ն է։

### `figma-to-production`

Դիզայնից UI, երբ հավելված և դիզայնի համակարգ կան։ Փոքր տեքստային ուղղման համար չէ։ Կանգ է առնում, եթե դիզայնը հասանելի չէ կամ փոփոխությունը չհաստատված ճարտարապետություն է պահանջում։

### Library skill-եր

Գործող workflow չեն, քանի դեռ տեղադրիչը դրանք չի տեղափոխել `.agents/skills/`։

| Skill | Ինչի համար է |
| --- | --- |
| `code-review` | Diff-ի կամ pull request-ի անկախ review։ |
| `security-review` | Ապացույցով անվտանգության review. auth, իրավունք, վճարում, webhook, ֆայլ, անձնական տվյալ։ Մշտական կանոնը չի փոխարինում։ |
| `react-performance-review` | React և Next.js արդյունավետության review, երբ այդ stack-ը գոյություն ունի և review-ն առանձին է խնդրված։ |
| `ui-accessibility-review` | Մատչելիություն, ստեղնաշար, ֆոկուս, ձև։ Միակ արտաքինից հարմարեցված փաթեթն է։ Աղբյուրը գրված է `SOURCE.md`-ում և `sources.lock.json`-ում։ |

`profiles.json`-ի պրոֆիլները agent-ի workflow խմբեր են. `core`, `frontend`, `backend`, `security-sensitive`, `fullstack`, `greenfield`։ Դրանք Meduzellar-ի օգտատիրոջ կամ Office հաշիվ չեն։ `greenfield`-ը չի ժառանգում `security-sensitive`-ը։ Պրոֆիլում լինելը library skill-ը չի միացնում։

## Կաղապարներ

`docs/reference/templates/`-ի ֆայլը պատճենելը որոշում չի ստեղծում։

### `TECH_CARD_TEMPLATE.md`

Դատարկ տեխնոլոգիական քարտ։ Արժեքի սյունակը դատարկ է։ Decision state-ը կարող է լինել դատարկ, `Candidate`, `Proposed`, `Approved` կամ `Rejected`։ Միայն `Approved`-ն է թույլատրում այդ արժեքով շարունակել։ Նշում սյունակը չափանիշ է, ոչ թե ընտրված արժեք։

Բաժինները հիմք, frontend, backend, բազա, նույնականացում, պահոց, արտաքին ծառայություն, հոսթինգ, թեստ, անվտանգության նպատակ, փաստաթուղթ և ավարտի ստուգում են։ Նույնականացման բաժինը դատարկ հարցաթերթիկ է։ Զրույցի identity նախընտրությունը այստեղ չի գրվում։ Անվտանգության բաժինը վերահսկողության նպատակ է, ոչ թե մատակարար։

Լրացված պատճենի ուղին կլինի `docs/TECH_CARD.md`։ Այդ ֆայլը հիմա չկա։

### `ARCHITECTURE_TEMPLATE.md`

Դատարկ ճարտարապետության ձև։ Տեխնոլոգիայի տեղը դատարկ է, քանի դեռ արժեքը TECH_CARD-ում `Approved` չէ։ Գծապատկերը չի նշում Next, Nest կամ Postgres։ Կապված փաստաթղթերի հին կոտրված հղումները հանված են։ Կանոնական ուղիները գրված են որպես տեքստ, ոչ թե որպես գոյություն չունեցող ֆայլի հղում։ `docs/04-API.md`, `docs/05-DATABASE.md` և `docs/DECISIONS.md` կանոնական անուն չեն և չեն ստեղծվում այս ձևից։

Նոր նախագիծ սկսելու ձև. անուն, նպատակ, շրջանակ, ռիսկ, դատարկ stack աղյուսակ։ Stack աղյուսակը մատակարար չի ընտրում։ Պարտադիր փաստաթղթերի ցանկը ֆայլերը հիմա չի ստեղծում։ Գաղտնաբառի ալգորիթմը գրվում է միայն TECH_CARD-ի `Approved` արժեքով, եթե գաղտնաբառ ընդհանրապես պահվելու է։

### `ADR_TEMPLATE.md`

Ճարտարապետական որոշման գրառման ձև. համատեքստ, տարբերակներ, հետևանք։ Ներսում կա տեղապահ հղում `./ADR-XXX.md`, որը ֆայլ չէ։

### `docs/reference/Check/Security/`

Տասներկու ֆայլ։ Յուրաքանչյուրի սկզբում կա Meduzellar-ի կարգավիճակ. սա օրինակ է և հաստատված որոշում չէ։ Vendor-neutral վերահսկողությունը մնում է. վավերացում, սերվերային լիազորություն, պարամետրացված հարցում, գաղտնիքը ռեպոյից դուրս, անվտանգ սխալ և լոգ։ Կոնկրետ արտադրանքի քայլը գործում է միայն `Approved` արժեքից հետո։

## Ստուգիչ և GitHub ձևեր

`scripts/validate-agent-config.mjs`-ը կարդում է skill-երը, library-ն, կանոնները, catalog-ը և ներքին Markdown հղումները։ `pnpm lint`-ը և `pnpm run build`-ը հիմա հենց այս ստուգիչն են գործարկում։ Սա հավելվածի build չէ։ Այն չի ստուգում, թե արդյոք որևէ նախադասություն թույլ է տալիս շրջանցել անվտանգության սահմանը։

`.github/PULL_REQUEST_TEMPLATE.md`-ը pull request-ի հայերեն ձև է և ունի README-ի շրջանակը ստուգելու կետ։ `.github/ISSUE_TEMPLATE/`-ում կան bug և feature ձևեր։ `.github/dependabot.yml`-ը հետևում է GitHub Actions-ին։ npm բլոկը մեկնաբանության մեջ է, որովհետև հավելվածի կախվածություն չկա։
